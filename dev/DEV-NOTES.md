# BVM GPU experiment: Windows 11 ARM64 guest D3D11 acceleration on Raspberry Pi 5

Living progress log. **Read this first in a new chat, and keep it updated** as work continues
(append to the chronology, update "Current status" and "Patch inventory").

Last updated: 2026-10-21 (after item 52: lavapipe tessellation offload passed its feasibility test and is implemented in DXVK (dxvk_tessemu.cpp), untested at runtime; goal: Explorer icons / tab bar).

## Goal

Make DirectX 11 hardware acceleration work in a Windows 11 ARM64 QEMU/KVM guest on a Raspberry Pi 5
(Pi OS Bookworm 64-bit, Broadcom V3D 7.1 GPU), using the UTM stack:

- **Triton**: signed WDDM guest driver (`viogpu3d.inf`, from `osy/kvm-guest-drivers-windows` releases, v0.4).
- **Neptune**: virglrenderer extension (`utmapp/virglrenderer`, branch `staging/neptune-linux`) that receives the
  guest's D3D11 command stream on the host and executes it through **DXVK** (D3D11 -> Vulkan) on the Pi's **V3DV**.
- QEMU `utm-edition` fork providing `virtio-gpu-gl-pci,...,neptune=true`.

Success = hardware-accelerated graphics verified inside Windows (desktop renders, DWM stable, a D3D11 app runs
on the V3D GPU). If it works, the changes get merged into BVM (`~/bvm/bvm`, a bash script) as an
**experimental mode**. Not merge-ready yet.

Upstream marks Triton/Neptune as experimental and it is only designed for Apple/Linux desktop GPUs. V3D lacks many
features DXVK normally requires, so much of this work is bending DXVK/Mesa/the protocol to V3D.

### Standard test command

```
cd ~/bvm-gpu          # core dumps land in the cwd of the render-server worker
ulimit -c unlimited   # only needed when chasing a crash (cores are ~500 MB each; delete them afterwards)
MESA_SPIRV_FAIL_DUMP_PATH=$HOME/bvm-gpu/spirv-fail NPT_CAPS_SHIM=1 \
  ~/bvm-gpu/bvm-gpu-experiment run ~/win11 > ~/bvm-gpu/run-diagN.log 2>&1
```

- Default display is the gtk window (`gtk,gl=on,grab-on-hover=on`); the guest resolution follows the window (unmaximize/re-maximize to resize). Stop QEMU with Ctrl+C in the terminal or shut Windows down.
- Headless alternative: `GPU_DISPLAY='egl-headless,rendernode=/dev/dri/renderD128' EXTRA_QEMU='-vnc :0 -no-shutdown'`, then VNC `localhost:5900` or RDP (`~/bvm/bvm connect ~/win11`). - Optional: `NPT_TRACE=1` logs every Neptune command (huge). `-no-shutdown` (via `EXTRA_QEMU`) keeps QEMU paused if the guest powers off, so the last screen stays visible.
- (Outdated: `sdl` used to crash for lack of dmabuf scanout, fixed by item 91; SDL fullscreen is now the launcher default, item 144. GTK: `GPU_DISPLAY='gtk,gl=on,grab-on-hover=on'`.) `gtk gl=es` had eglMakeCurrent failures.
- Log triage: `grep -n 'DIED\|Unknown intrinsic\|v3dv:\|err:' run-diagN.log`. A worker death is a SIGSEGV/SIGABRT in the Neptune context; get a backtrace from the core with
  `gdb -batch -ex 'bt 20' ~/bvm-gpu/sysroot/usr/local/libexec/virgl_render_server ./core`. Failing shaders are dumped to `~/bvm-gpu/spirv-fail/` (`spirv-dis`).
- Rebuilding: see **Rebuild cheat-sheet** below. **`reset STEP` only forgets a step; nothing compiles until you run `setup`.**

### Rebuild cheat-sheet

The script remembers finished steps in `~/bvm-gpu/.done/`. `reset STEP` deletes that marker; `setup` then re-runs
every missing step (and only those). Always finish with `setup`, then `run`. Changes to the clones in
`~/bvm-gpu/{dxvk,virglrenderer,qemu,mesa-src}` are picked up by the matching build step.

**Shortcut:** `~/bvm-gpu/rebuild.sh dxvk|virgl|qemu|mesa|all` does reset + setup (or ninja for Mesa) in one go. Use it.

| I changed... | Rebuild |
|---|---|
| Mesa V3DV (`mesa-src/`) | `ninja -C ~/bvm-gpu/mesa-src/builddir install` (incremental, no script step) |
| DXVK (`dxvk/`) | `~/bvm-gpu/bvm-gpu-experiment reset build-dxvk` then `~/bvm-gpu/bvm-gpu-experiment setup ~/win11` |
| virglrenderer / Neptune (`virglrenderer/`) | `reset build-virgl` then `setup ~/win11` |
| QEMU (`qemu/`) | `reset build-qemu` then `setup ~/win11` |
| virglrenderer **and** QEMU | `reset build-virgl`, `reset build-qemu`, then `setup ~/win11` |
| Only `bvm-gpu-experiment` options/launch line | nothing, just `run` |

Example (QEMU display patch):
```
~/bvm-gpu/bvm-gpu-experiment reset build-qemu
~/bvm-gpu/bvm-gpu-experiment setup ~/win11        # this is the step that actually compiles
BVM_GL_NOBLOCK=1 VM_RAM=4G VM_SMP=3 NPT_CAPS_SHIM=1 ~/bvm-gpu/bvm-gpu-experiment run ~/win11 > ~/bvm-gpu/run-diagN.log 2>&1
```
Check with `~/bvm-gpu/bvm-gpu-experiment status` (`pending build-qemu` = not yet rebuilt).

## Host facts

- Pi 5, kernel 6.12 rpt, QEMU 10.0.2 system package (the custom build in `sysroot` is what runs), system Mesa 24.2.8.
- System V3DV 24.2.8 reports Vulkan 1.2 (DXVK needs 1.3) -> we use Mesa 25.0.7 V3DV (Vulkan 1.3.305) via `VK_DRIVER_FILES`.
- `/dev/udmabuf` exists; render node `/dev/dri/renderD128` is V3D. wayvnc (rpi-connect) uses a unix socket, no conflict with `-vnc :0`.
- V3D 7.1 hardware/driver gaps: no dual-source blend, multiViewport, shaderCullDistance, BC4-7, shaderInt64/16/8, descriptor
  indexing, tessellation, typed-UAV stores; **no sampling of linear (raster) 2D images**; no VK_KHR_maintenance6.

## Chronology: problems and solutions

Hashes: virglrenderer `cf5af71` (staging/neptune-linux), DXVK `e3386161` (osy/dxvk, last commit with
`dxvk_shared_resource.h`), neptune-protocol `0e0c939`, guest driver v0.4, Mesa tag `mesa-25.0.7`.

1. **Research and setup.** Found UTM 5.0.4+'s Triton/Neptune design (guest WDDM driver + host virglrenderer/DXVK).
   Wrote `bvm-gpu-experiment` to build the stack into `sysroot` without touching the system (deps, clones, builds, driver ISO).
2. **Vulkan 1.2 -> 1.3.** `mesa25-vulkan` step unpacks Mesa 25.0.7's Vulkan drivers from bookworm-backports and points an ICD json at them.
   (`MESA_VK_VERSION_OVERRIDE` has no effect.)
3. **DXVK push constants.** DXVK needs `maxPushConstantsSize >= 256`; V3DV advertises 128 via a `#define`. `mesa-v3dv` step builds
   V3DV from the 25.0.7 tag with `MAX_PUSH_CONSTANTS_SIZE` 256.
4. **DXVK refuses V3D.** `patch-dxvk` demotes features V3D lacks from required to optional in `dxvk_device_info.cpp`
   (dualSrcBlend, multiDrawIndirect, multiViewport, textureCompressionBC, shaderCullDistance, shaderInt64/16/8, shaderDrawParameters,
   descriptor-indexing group, robustBufferAccess2, nullDescriptor, **maintenance6**, ext khrPipelineLibrary). DXVK then creates a device.
5. **Feature level.** `patch-dxvk-fl` ignores multiDrawIndirect and tessellationShader in `GetMaxFeatureLevel` so DXVK reports FL 11_1.
6. **Build issues.** DXVK `native_dmabuf` option no longer exists; built with `-Dnative_headless=true`, SDL/GLFW off. virglrenderer built with
   `-Dneptune=true -Dvenus=true -Dtests=false -Dplatforms=egl -Wno-error=pedantic`.
7. **Guest/host protocol skew** (upstream header lag; candidates for upstream bug reports):
   - CheckFeatureSupport in/out data differed -> `sync-protocol` regenerates host protocol headers from `osy/neptune-protocol` (meson+mako).
     Originals are in `neptune-protocol.orig`.
   - Host `struct npt_cmd_resource_update` lacked `uint64_t context_id` after `pad` -> `patch-transport`. Fixed
     "failed to peek 24 bytes" and "RING_DESTROY must not originate from a ring".
   - Found with opt-in ring diagnostics (`diag-virgl-ring.patch`, `npt_ring_dump_failure`).
8. **llvmpipe cross-check was unreliable.** With llvmpipe the guest reached swapchain creation, but LLVM 15's JIT crashes
   (`LLVM ERROR: Cannot select ...`), so it can't be used as a reference renderer. Only its capability *answers* were useful.
9. **V3D: DWM crash loop.** On V3D the guest created ~115-120 Neptune contexts per minute and never a swapchain. Guest event logs: `dwm.exe`
   crashes in `dwmcore.dll` (0x889800b0, 0xc00001ad), 97 crashes in accelerated boots, 0 in the basic-display control boot.
   Call tracing (`NPT_TRACE=1`, added to `npt_context.c` and the generated `npt_protocol_host_id3d11device.h` reply logging) showed the guest probes
   formats/features, then discards the device. Differential trace V3D vs llvmpipe: V3D stops after 14 formats; missing typed-UAV bits,
   R32G32B32/R16G16B16A16 support, FORMAT_SUPPORT2, doubles, min precision, tiled resources, etc.
10. **Capability shim (`NPT_CAPS_SHIM=1`).** In `npt_overrides_shared_handle.c`, overrides `CheckFormatSupport`/`CheckFeatureSupport` to raise
    V3D's answers to llvmpipe's (tables `bvm_fmt_floor[]`, `bvm_sup2[]`; doubles=1, min precision, OPTIONS2/3). Windows then passed the probe and created swapchains
    (23 `npt: shared: exported` lines). It is a lie about the hardware: features DWM then actually uses may fail.
11. **DXVK global buffer failure** ("Failed to create global buffer", "Got allocation from memory type 0 without global buffer").
    V3DV pads buffer memory requirements (requirement > allocation size for some sizes). Patched `dxvk_memory.cpp`: shrink the buffer by the pad and
    accept `requirement <= size` (previously required exact equality).
12. **Intermittent short runs.** About 30% of QEMU runs exit with code 0 after ~30 s at low CPU and the log stays at ~272 bytes (no Neptune contexts). VNC shows tianocore.
    Cause not investigated. Mitigation: rerun; `-no-shutdown` keeps the VM visible. Possibly Windows failing to boot after many forced crashes (consider restoring the disk backup).
13. **Shared-image export refused** ("no usable modifier for format B8G8R8A8_UNORM", then "texture ... not found"): the guest sets a vendor
    "linear export" bit, but V3D's linear modifier can't be sampled. Patched `dxvk_image.cpp` canShareDmabufImage: pass 0 honors force-linear,
    pass 1 falls back to any modifier (Broadcom UIF `0x0700000000000006`).
14. **Worker SIGSEGV on first draw.** Core dump + gdb showed a null function pointer call in `DxvkContext::updateDescriptorSetsBindings` ->
    `vkCmdBindDescriptorSets2KHR` (VK_KHR_maintenance6, absent on V3DV, demoted to optional in step 4). Patched `dxvk_cmdlist.h` with
    fallbacks to core `vkCmdBindDescriptorSets` and `vkCmdPushConstants`.
    (Core procedure: `ulimit -c unlimited` in the shell, run from `~/bvm-gpu`, `gdb -batch -ex 'bt 25' <sysroot>/usr/local/libexec/virgl_render_server ./core`.)
15. **Cursor-sized image import failed** (32x32 `R8`, error -1000158000 = INVALID_DRM_FORMAT_MODIFIER_PLANE_LAYOUT_EXT). V3DV's import check demanded UIF pitch alignment for every
    tiled image, but its own export of small (LINEARTILE) images reports an unaligned pitch. Patched Mesa `v3dv_image.c` to enforce the
    alignment only for UIF tilings (also added to the `mesa-v3dv` step in the script).
16. **First visible success:** Windows boot animation completes and the login screen background is rendered (VNC shows a blue gradient).
    Image is garbled with a repeating ~256x20 pattern.
17. **Garbled scanout = modifier lost.** V3D can't sample linear images, so swapchain buffers are UIF-tiled; QEMU builds the scanout dmabuf with modifier hard-coded `0`
    (linear), so EGL reads tiled memory as raster. Plumbed `export_modifier` end to end: Neptune pending blob -> `virgl_context_blob` -> render-server reply
    (`render_protocol.h`) -> proxy -> `virgl_resource` -> `virgl_renderer_resource_get_info_ext().modifiers`; QEMU records it at blob creation
    (`virtio_gpu_simple_resource.dmabuf_modifier`) and passes it to `qemu_dmabuf_new`.
18. **Login screen renders correctly, login succeeds** (run-diag9, 2026-10-20). Log is clean: no `err:` lines, no worker deaths, no dead contexts,
    only 7 contexts in 2 minutes (the churn is gone). The run ended because of the `timeout 120` wrapper, so desktop stability is untested.

19. **Desktop freezes opening Task Manager (DWM worker SIGSEGV).** Core (run-diag10): null deref in V3DV `link_shaders` <- `pipeline_init` <-
    `vkCreateGraphicsPipelines` <- DXVK `createOptimizedPipeline`. Cause: `shader_module_compile_to_nir` returned NULL (a SPIR-V shader DXVK
    emitted that V3DV can't translate; Mesa release builds log nothing) and `v3dv_pipeline.c` linked it anyway. Patched `v3dv_pipeline.c` to fail the
    pipeline cleanly and print `v3dv: SPIR-V to NIR failed (vs=.. gs=.. fs=..)`. To find the offending shader, run with
    `MESA_SPIRV_FAIL_DUMP_PATH=~/bvm-gpu/spirv-fail` and disassemble with `spirv-dis`. Also seen once: `D3D11Buffer: Failed to import 1048576-byte dmabuf`.

20. **Hardware acceleration confirmed in the guest** (2026-10-20): Task Manager and dxdiag show "Red Hat VirtIO GPU 3D controller", driver
    `neptune_umd.dll` 100.6.101.58000, WDDM 2.2, Direct3D DDI 11.1, feature levels 11_1..9_1, Direct3D acceleration Enabled, edge://gpu all hardware accelerated.
    Run 11 (gtk display): no worker deaths. The only host error is a tessellation pipeline (VS+HS+DS, patch list, R32G32_SFLOAT) which V3DV can't compile
    (`Failed to compile pipeline: -13`); DXVK skips those draws, so tessellated 2D geometry (some UI) is missing. We claim FL 11_1 (needs tessellation) via `patch-dxvk-fl`.
    Suspected: PowerShell/Windows Terminal text glitch (white on white) = ClearType dual-source blending, which V3D lacks. Test: Windows Terminal > Settings > Defaults > Appearance
    > Text antialiasing = Grayscale.
21. **Script option added:** `SHARE_DIR` (default `$HOME`, served by QEMU's built-in Samba as `\\10.0.2.4\qemu`; `SHARE_DIR=` disables).
    The old `\\tsclient\_home_pi` share only exists over RDP (`bvm connect`), not with the gtk display. Windows 11 may need
    `Set-SmbClientConfiguration -EnableInsecureGuestLogons $true -Force` (admin PowerShell) for guest SMB. Not yet confirmed working.
    Resolution: a `GPU_RES` option was added and then **reverted** (2026-10-20). The guest follows the QEMU gtk window size: unmaximize and
    re-maximize the window and Windows resizes the desktop. No QEMU flag needed.

22. **WebGL Aquarium freezes the whole Edge window (worker SIGABRT).** Log: `Unknown intrinsic: ... @load_first_vertex` then `worker ... DIED on signal 6`; core in
    `ntq_emit_intrinsic` (V3D compiler `unreachable`/abort in release builds). Cause: dxbc-spirv declares `BuiltInBaseVertex` (+DrawParameters capability) for every shader
    reading SV_VertexID to compute `VertexIndex - BaseVertex`; V3DV has `shaderDrawParameters=false` and no `load_first_vertex` support. Patched DXVK:
    new `DxvkShaderSpirvFlag::NoBaseVertex` (set in `dxvk_device.cpp` when the device lacks shaderDrawParameters) -> `SpirvBuilder::Options::noBaseVertex`
    (`dxvk/subprojects/dxbc-spirv/spirv/spirv_builder.{h,cpp}`, `src/dxvk/dxvk_shader_ir.cpp`): skip BaseVertex and use VertexIndex unchanged.
    Known inaccuracy: SV_VertexID then includes BaseVertexLocation for indexed draws with a nonzero base vertex. BaseInstance is still used (not yet proven to fail).
    Untested.

23. **Windows Terminal / XAML text is clipped and occluded** (settings page labels cut off vertically/horizontally, terminal preview shows white boxes with partial black glyphs).
    Not only ClearType colour: parts of text are missing, which points at skipped draws. Host log of run-diag12 (stable, no worker deaths) shows two `Failed to compile pipeline: -13`
    (VS+HS+DS tessellation, patch list, `R16G16_SINT` target with logic op: looks like Direct2D/XAML GPU geometry, e.g. clip/mask) and two `D3D11Buffer: Failed to import 1048576-byte dmabuf`.
    Test idea (no rebuild): cap DXVK's feature level to 10_1 so apps never create hull/domain shaders: `DXVK_CONFIG='d3d11.maxFeatureLevel = 10_1'` in the environment of `run`.

86. **Root cause and fix: dynamic sampler indexing in V3D (2026-10-26/27).** Cause: `lower_tex_src` (`v3dv_pipeline.c`) turns a dynamic sampler deref into `nir_tex_src_sampler_offset`, but nothing in `src/broadcom/compiler` consumed it (`handle_tex_src` falls into `unreachable("unknown texture source")`, silently ignored in release builds), and the sampler state address is a CPU-resolved uniform (`QUNIFORM_TMU_CONFIG_P1`, driver `write_tmu_p1` replaces `sampler_idx<<24` with the address of array element 0). Fix (Mesa patch, 2 files): (a) `v3dv_pipeline.c`: for a dynamically indexed sampler the index is clamped to `binding_layout->array_size-1` and scaled to a byte offset (`descriptor_bo_size(type) * plane_stride`); (b) `compiler/v3d_tex.c`: `handle_tex_src` accepts `nir_tex_src_sampler_offset`/`texture_offset` (fetched early so a TMU flush cannot land inside the config writes; texture offset still unused, DXVK does not need it), and `v3d_vir_emit_tex` writes P1 as a register: `TMUC = uniform(P1 base) + offset` (`vir_TMU_WRITE(c, V3D_QPU_WADDR_TMUC, vir_ADD(...))`) instead of the `wrtmuc` uniform signal. The offset is a multiple of the descriptor size so the flag bits in the low bits stay intact; the scheduler already supports TMUC register writes. Verified: `pattern.html` tiles at every size (Canvas2D and WebGL), slither.io background correct, no regressions seen. Rebuild: `~/bvm-gpu/rebuild.sh mesa`. Upstream candidate: V3DV silently ignores dynamic sampler indexing (`shaderSampledImageArrayDynamicIndexing` is reported false, but descriptor-indexing style indexing still reaches the compiler). Side effect: every filter/wrap mode DXVK asks for is now honoured per draw, which was never the case before.

# Part 3: notes of the removed `remove_UCPD_from_mountpoint` function

BVM used to delete `Windows/System32/drivers/UCPD.sys` from the disk (and restart QEMU once) when QEMU ended within 240 seconds, to avoid a bluescreen reported in https://github.com/Botspot/bvm/issues/72.
It was removed on 2026-11-18: on the development image (Windows 26100.9711) UCPD.sys is back (restored by Windows Update, dated 2026-11-06) and the VM runs fine. Now a clean exit within 240 seconds only prints a hint to try `boot-ramfb`.
How the problem was diagnosed, in the author's words:

```
To diagnose: boot, get it to crash, shutdown.
find most recent crash dump in C:/Windows/Minidump
copy it out and analyze on another computer:

Download WinDbg Preview from the Microsoft Store
Open WinDbg, go to File > Open Crash Dump, select the .dmp file.
Run: !analyze -v
Look for: MODULE_NAME or IMAGE_NAME

In this case:
MODULE_NAME: UCPD
IMAGE_NAME:  UCPD.sys

workaround until fixed:
boot-ramfb, F8 to get boot modes, 5 to boot in safe mode with networking

location of UCPD.sys: Windows/System32/drivers/UCPD.sys
```
